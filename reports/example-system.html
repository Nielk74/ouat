Move scheduled exports into worker processes

Four focused changes: enqueue work, configure the producer, run bounded worker threads, and deploy the consumer independently.

4 summarized code changes

01

Context

Problem / goal

Export work runs inside the API request process. That request stays open until the export finishes; stopping the API process interrupts the in-flight job.

Comparison baseline

Illustrative baseline: every five minutes, cron calls the API. The API awaits buildExport(), stores the result, then replies done. There is no queued handoff or independent consumer.

Scope

One hypothetical solution. The paths, before/after excerpts, and infrastructure below are illustrative, not inspected project files.

Constraints

  • Accept a job only after durable queue publication; acknowledge it after storing its result.
  • Bound concurrency and preserve the job ID across delivery attempts.

Assumptions / unknowns

  • The broker supports durable delivery and the existing results table has a unique job ID.
  • The illustrative consume wrapper acknowledges only after its callback succeeds.
  • RabbitMQ, PostgreSQL, and TeamCity are illustrative product choices here, not findings about this project.

Proposed changes

01

Publish a job instead of building inline

Changed · proposed

The producer returns a queued job handle. Export execution moves to a consumer.

BeforeExcerpt lines

1+const job = { id: jobId, accountId };2+await exportQueue.publish(job);3+return { status: "queued", jobId };

Replace one inline call with durable publication; completion becomes asynchronous.

Why. Keep long-running work outside the API request lifecycle.

03

Consume work in a bounded thread pool

New · proposed

A separate consumer process starts two worker threads and persists results by job ID.

1+const pool = new WorkerPool({ size: config.workers });2+await consume(async job => {3+  const artifact = await pool.run(job);4+  await results.upsert(job.id, artifact);5+});

Start the pool once; run each delivered job in a worker thread and upsert its result before acknowledging.

Why. Isolate execution from the API and cap simultaneous export work.

Deploy the consumer independently

Changed · proposed

04

Expected impact

Publish a job instead of building inlineExpected

The API returns a queued job handle; completion becomes eventual. Callers must use the job ID to inspect the result.

Put routing and concurrency in configurationExpected

The cadence stays the same. Queue routing and concurrency become operational settings.

Consume work in a bounded thread poolExpected

At most two jobs execute per worker host. Re-delivered jobs update the same result key; execution still consumes resources.

Deploy the consumer independentlyExpected

The worker can restart independently of the API. Delivery depends on a healthy consumer and a correctly configured broker binding.

05

Important risks

important riskConsume work in a bounded thread pool

A job can be delivered more than once

When: A consumer stops after saving a result but before acknowledging delivery.

Consequence: The job can run again, consuming extra resources or repeating other side effects.

Mitigation: Keep the stable job ID, upsert its result, and make any additional effects idempotent.

important riskDeploy the consumer independently

Jobs accumulate without a healthy consumer

When: The worker is stopped or its queue binding is wrong.

Consequence: The API can accept jobs while completion is delayed.

Mitigation: Verify consumption after deployment and monitor queue age and worker health.
